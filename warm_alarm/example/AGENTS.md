# warm_alarm/example

Runnable Flutter app demoing the plugin **and** the host for Fluttium E2E flows. Three native shells (Android / iOS / macOS) plus a nested Fluttium custom-action package.

## STRUCTURE

```plaintext
lib/main.dart                                # voice alarm demo UI + readiness inspection + event log
lib/voice_audio.dart                         # example-only recording, preview, and app-private files
fluttium.yaml                                # registers custom actions for Fluttium
flows/test_readiness.yaml                    # the only E2E flow (presses "Inspect Alarm API" then runs `checkReadiness`)
integration_test/app_test.dart               # standard integration_test entry (used by flutter_driver)
test_driver/integration_test.dart            # driver entry
actions/check_readiness/                     # standalone Dart pkg providing the `checkReadiness` Fluttium action
android/, ios/, macos/                       # default Flutter native shells (regenerated by `flutter create`)
```

## WHERE TO LOOK

| Task                               | Location                                                                                    |
| ---------------------------------- | ------------------------------------------------------------------------------------------- |
| Demo UI changes                    | `lib/main.dart`                                                                             |
| Add a new Fluttium step (built-in) | `flows/test_readiness.yaml` (or add a new `flows/*.yaml`)                                   |
| Add a custom Fluttium action       | `actions/<name>/lib/src/<name>.dart` + register in `fluttium.yaml` under `actions:`         |
| Run E2E locally                    | `fluttium test flows/test_readiness.yaml -d <android\|iPhone\|macos>` (from this directory) |

## CONVENTIONS

- `pubspec.yaml` path-depends on `warm_alarm` and its public platform interface.
  Endorsed platform implementations are resolved through `warm_alarm`.
- This package is part of the root Dart workspace (declared in root `pubspec.yaml`) **and** is included in Melos's package list, so Melos scripts (`format`, `test`, `generate`-if-applicable) target it.
- The nested `actions/check_readiness/` package is in the root Dart workspace and is discovered by Melos even though it is absent from the `melos.packages` list.
  Melos test commands include it; use `melos list` to inspect the resolved package set.
- The readiness CI flow runs on an Android API 29 emulator and an iPhone simulator only for `workflow_dispatch` or a `v*` tag — see `.github/workflows/warm_alarm.yaml`.
  Ordinary PRs and package publication tags such as `warm_alarm-v0.1.8` do not run these E2E jobs.
  macOS readiness remains a manual Fluttium check; the separate native macOS workflow does not run this UI flow.
- `lib/main.dart` is a State-driven `MaterialApp` with no router or state-management framework.
  Keep example-only audio I/O in `lib/voice_audio.dart`; inject it in widget tests so tests never request the microphone.
  Preserve the readiness action labels used by Fluttium and the presentation scripts.

## ANTI-PATTERNS

- Don't edit anything under `android/app/src/main/java/io/flutter/plugins/GeneratedPluginRegistrant.java`, `ios/Flutter/Generated.xcconfig`, `macos/Flutter/ephemeral/`, or any other `Generated*`/`flutter_export_environment.sh` file. They're regenerated.
- Don't ship a release build with the placeholder `applicationId` / signing config in `android/app/build.gradle.kts`.
- Don't add new top-level packages under `actions/` and forget to register them in `fluttium.yaml` — Fluttium will not auto-discover them.
- Don't promote example-only utilities into the public plugin packages.

## NOTES

- The Android host uses AGP 9.0.1, Kotlin 2.3.20, and Gradle 9.2.1.
  Keep `android.newDsl=false` and `android.builtInKotlin=false` in its `gradle.properties` while Flutter uses the legacy Android DSL and this plugin applies the external Kotlin plugin.
  Direct native Gradle jobs do not run Flutter build migrations.
  Keep the wrapper distribution's published SHA-256 checksum pinned for both local builds and CI downloads.

- `flows/test_readiness.yaml` is intentionally tiny — it presses the "Inspect Alarm API" button (key/text in `lib/main.dart`) and invokes the custom `checkReadiness` action. If you rename the button text, update the flow.
- The `actions/check_readiness/` package depends on `fluttium: ^0.1.0`. It is consumed at flow-execution time, not at app build time, so changes there don't require a Flutter rebuild — just re-run the flow.
