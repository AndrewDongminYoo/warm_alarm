## Commands

**Workspace setup**

```bash
flutter pub get          # resolve dependencies across all packages
```

**Melos scripts (run from repo root)**

```bash
melos run generate       # regenerate all Pigeon platform-channel bindings
melos run test           # run unit tests across all packages
melos run test:ci        # run tests with coverage output (concurrency 4)
melos run format         # format Dart code + apply dart fixes (120-col)
melos run format:ci      # format and exit nonzero if files changed
```

**Quality checks**

```bash
trunk check              # Spelling, Markdown, YAML, Kotlin linting; Dart uses project commands
```

**Integration tests** (requires `fluttium_cli` installed globally)

```bash
cd warm_alarm/example && fluttium test flows/test_readiness.yaml -d macos
cd warm_alarm/example && fluttium test flows/test_readiness.yaml -d android
```

## Architecture

Five packages in a Melos workspace:

| Package                         | Role                                                  |
| ------------------------------- | ----------------------------------------------------- |
| `warm_alarm`                    | Public API facade + runnable example app              |
| `warm_alarm_platform_interface` | Abstract platform contract; all platforms extend this |
| `warm_alarm_android`            | Android implementation                                |
| `warm_alarm_ios`                | iOS implementation                                    |
| `warm_alarm_macos`              | macOS implementation                                  |

### Platform communication via Pigeon

All native ↔ Dart communication is code-generated by Pigeon. The schema lives in `pigeons/messages.dart`
in each platform package. Generated outputs — `lib/src/messages.g.dart`, `Messages.g.kt`,
`Messages.g.swift` — are never hand-edited. After any `pigeons/messages.dart` change, run
`melos run generate`.

### Model boundary rule

Public-facing model classes are hand-written in `warm_alarm_platform_interface/lib/` and designed
for API stability. Pigeon-generated DTO types stay in `lib/src/` (private) and are never re-exported.

### Platform implementation pattern

Each platform package: (1) extends `WarmAlarmPlatform` from the interface package, (2) registers
via `static void registerWith(Registrar)`, (3) delegates to the Pigeon-generated `WarmAlarmApi`.

## Before committing

For scoped changes, pass the changed paths explicitly:

```bash
dart format <changed-dart-files>
trunk fmt <changed-files>
```

Run `melos run generate` when a Pigeon schema or generator version changes.
The workspace-wide `melos run format` also applies Dart fixes, so use it only when that broader scope is intended.
For a read-only Dart format check, use `dart format --output=none --set-exit-if-changed <changed-dart-files>`.

## Key constraints

- Line length: 120 columns (not the Dart default 80); configured in each `analysis_options.yaml`.
- Mocking: use `mocktail`, not `mockito`.
- Tests live in the package where the tested code lives.
- Commits follow Conventional Commits (`feat:`, `fix:`, `chore:`, `ci:`, etc.).
- Design spec and Phase 1A implementation plan are in `docs/`.
